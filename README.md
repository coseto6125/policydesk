# policydesk

一個保險櫃台 agent：從方案、簽約、繳費、保額到理賠，全流程都由同一個 agent 承接。

它報出的每一個金額都帶著條款出處。沒有出處的數字不會出現在畫面上，因為型別不允許。

## 為什麼需要條款層

保單條款有兩種陷阱，只做關鍵字檢索的工具會踩進去。兩個都出自我們索引的第一份真實
合約（國泰人壽全心住院日額健康保險附約，16 頁，38,657 字，24 條）。

**陷阱一：等待期不叫等待期。** 全文搜尋「等待期」命中 0 次。三十天的等待期寫在封面
「疾病」的定義括號裡：

> 本險「疾病」之定義：係指被保險人自本附約生效日起持續有效**三十日以後**或復效日起
> 所發生的疾病。

檢索「等待期」的工具找不到它，於是放行一筆生效第 20 天發病的申請，整筆算錯。

**陷阱二：除外責任在同一句話裡回復承保。** 第十七條：

> 一、美容手術、外科整型。**但為重建其基本功能所作之必要整型，不在此限**。

只撈到前半句就拒賠，只撈到後半句就照賠，兩種都錯。判斷條件是「是否為重建基本功能」，
那要看病歷怎麼寫，所以它必須落到人工，不能落到模型。

## 設計

**索引是確定性的。** `clauses/index.py` 從 PDF 切出條號、判斷條款種類、把回復承保
從除外責任裡拆出來、把偽裝成定義的等待期還原成獨立條款。這一段不呼叫模型。

**模型只能引用，不能撰寫。** `Citation` 只能由 `ClauseIndex.cite()` 產生，而它會對
不存在的條號拋 `KeyError`。捏造的引用在這裡是當場崩潰，不是一個看起來合理的數字。

**金額必須帶證據。** `Money` 沒有 citation 就無法建構。`ClaimItem` 若判定不是
`PAYABLE` 卻帶著金額，同樣拒絕建構，避免它混進總額。

**判不了的要說判不了。** `Verdict.NEEDS_HUMAN` 用於證據不足、條款衝突無法解析，
或判準是醫療而非契約。這類項目一律排除在總額之外。

## 目錄

| 路徑 | 職責 |
|---|---|
| `core/` | 領域模型。`Money`、`ClaimItem`、`Citation` 的不變式在這裡 |
| `clauses/` | 條款索引與引用。唯一能產生 `Citation` 的地方 |
| `skills/` | 五個環節：方案、簽約、繳費、保額、理賠。各自是確定性工具 |
| `agent/` | 編排。把自然語言轉成 skill 呼叫，不自行計算金額 |
| `gov/` | 身分驗證。政府 API 以 mock 實作 |
| `audit/` | 稽核軌跡。金管會 2026-05 代理 AI 規範要求的可追溯性 |

## 開發

```bash
uv sync --extra dev
./scripts/fetch_fixtures.sh   # 條款 PDF 屬保險公司版權，不進 git
uv run pytest
```

測試分兩層：純函式測試不需要 PDF；索引測試需要 fixture，缺檔案時自動 skip。
